# Strands Decider、Jev、GPT 与 BERT：本项目如何比较

本项目使用官方 `StrandsAgents/strands-decider-2B-hobson-v19`，不是直接将 Qwen 聊天模型改名。主体为 Qwen3.5-2B，配合 LoRA 与 Pointer Head；实现锁定到 [官方源码 63d24ae](https://github.com/strands-labs/strands-decider/tree/63d24ae286e50105fba0bd1db15b0e243aea4650/src/strands_decider)。

当前页面同时比较 Decider、Typesafe 托管 Jev 与 Bedrock GPT-6.1 Sol。Jev 接收相同的 System One `state`、`questions` 和候选条件，保留服务端返回的实际模型版本、选择与概率；不根据接口相同推断 Jev 使用了与 Decider 相同的内部结构或 confidence 公式。接入细节见 [Jev 指南](JEV.md)。

2026-10-16 起，演示中的 Decider 统一使用官方 v19 的 vLLM 适配服务。下文已采集的性能与选择差异仍来自原版部署，不作为 vLLM 的复测结果。

## 当前三模型性能

数据来自 [2026-10-12 预热后三模型记录](presentations/v8/live-observations.json)：`triple1` 优化流程，四场景各五步，每步同时请求三个模型，输入与候选一致；每个场景运行一次。Jev 实际版本 `jev-1.13.0`；GPT 为 `us.openai.gpt-6.1-sol` / `low`；Decider 为 EC2 `g6.xlarge` 上的官方 v19。

| 指标 | Decider | Jev | GPT |
| --- | ---: | ---: | ---: |
| 成功调用 / 尝试 | 20/20 | 20/20 | 20/20 |
| 累计后端耗时 | 2.043 s | 8.329 s | 22.335 s |
| 平均每次后端耗时 | 102.2 ms | 416.5 ms | 1116.7 ms |
| 与演示参考一致 | 18/20 | 20/20 | 20/20 |
| 执行保护调整 | 1 次 | 0 次 | 0 次 |
| 初始场景资金及结案均完成 | 0/4 | 0/4 | 0/4 |

按未舍入的成功调用合计计算，Jev 耗时是 Decider 的 **4.08 倍**，GPT 是 Decider 的 **10.93 倍**，GPT 是 Jev 的 **2.68 倍**。这些是当前部署路径与固定样本的观测；不同网络、输入、推理配置及执行模式会改变结果。Jev 的计时包含 SDK、Lambda 和 HTTPS 往返，未获得纯模型推理时间。官方宣传与本项目口径的差异见 [测速解释](JEV.md#为什么没有官方宣传中的加速倍数)。

测试前各模型各调用一次，三次预热另行保留。正式 20 次 Jev 请求均复用了同一个已预热 Lambda 环境，日志没有 `Init Duration`；没有从时间中扣减估算开销。见 [逐请求验证](presentations/v8/lambda-warm-verification.json)。当前均值仍包含正常代理、连接和网络成本，不代表纯模型时间。

此前的连接失败、含冷启动测试及同输入重试保留于 [项目历史](HISTORY.md)。当前统计不混用这些记录，也不能将前后均值的变化全部归因于预热。

不同并发下的吞吐、客户端 p50/p95、成功率及后端等待分解见 [并发性能测试](CONCURRENCY.md)。该测试保持当前 Decider 一个执行槽、Jev/GPT 两个调用槽，反映现有应用承载能力，不代表模型或托管供应商的最大吞吐。

## 本批次选择差异与业务结果

| 场景 / 步骤 | Decider 原始选择 | Jev / GPT 原始选择 | 实际执行与最终状态 |
| --- | --- | --- | --- |
| USDC 未到账 | 五步均符合参考 | 五步均符合参考 | 确认数 3/12，资金挂起，工单跟进 |
| USDT 少付 / 核验 | 等待链上确认 | 请求补款 | 原始核验差异保留；仍差 0.20 USDT，三模型都挂起资金并跟进 |
| 稳定币退款 / 审批 | 规则检查通过 | 验证退款地址 | 执行器把 Decider 审批调整为验证地址；三模型均等待地址与人工审批，未退款 |
| 商户结算 | 五步均符合参考 | 五步均符合参考 | 结算未到账，升级结算工单并跟进，未完成对账 |

20 个步骤中有 18 个三模型选择相同。**两次参考差异与一次执行保护调整不是同一个指标**：少付核验的错误建议被保留；退款审批的过早通过被执行器调整。调整之后的动作仍不能计作 Decider 原始判断正确。

每个模型在每个案例中都处理了五步，但初始证据不具备资金和结案条件，所以三个模型均为 0/4 完成资金及结案。这是预期的初始业务状态，并不等于调用失败。用户推进确认、补款、地址验证、审批或结算事件后，才具备继续完成业务的条件；本表没有测量这些后续证据下的闭环完成率。

Jev / GPT 的 20/20 仅表示这个样本集与演示参考相符，不能解释为生产正确率 100%。三个模型都需要相同的应用执行校验；参考答案也不能自动视作金融行业规范。

## Decider 怎样得到一个选择

1. 应用提供业务状态 `state`、问题 `instructions`、候选项及其适用条件 `criteria`。
2. 提示构造器将它们编码为模型输入，并定位候选位置和答案位置。
3. Pointer Head 使用答案位置与候选位置的隐藏表示，经归一化、投影和点积得到候选 logits；按问题类型使用温度，再计算概率。
4. `choice` 取最高概率对应的候选。候选来自请求，模型不会临时发明新的业务动作。
5. 输出校验后，由应用执行器决定实际动作；模型本身没有资金权限。

这是可从公开实现核对的计算流程，不是模型输出的自然语言思维链。概率分布可以显示模型偏向哪个动作，不能证明它在某一次判断中“为什么忽略了某个条件”。

对于 `K > 1` 的 choice 问题，confidence 为 `clip((K × p_max − 1) / (K − 1), 0, 1)`；单候选为 1。它不同于最高候选概率，也不是金融业务正确率。`noul` 输出真概率，`score` 对有序等级计算期望；不要将 choice 的 confidence 公式套到所有类型。

## 与常见 BERT 分类器的区别

| 维度 | 常见 BERT + 固定分类头 | Strands Decider | 本项目 GPT-6.1 Sol |
| --- | --- | --- | --- |
| 类别含义 | 标签映射和监督训练定义 K 个输出维度 | 候选名称与条件随请求输入 | 提示中给出同样候选 |
| 输出方式 | 编码表示 → 固定 K 类分类头 | 对当前候选位置进行共享评分 | 自回归生成候选 ID JSON |
| 新增类别 | 通常改标签集、分类头并训练 / 微调 | 不必按 K 扩充固定输出头；仍需验证新任务能力 | 修改提示与候选；仍需验证条件遵循 |
| 典型用途 | 标签稳定、有领域标注的分类任务 | 候选变化、自然语言定义的有限选择 | 开放式生成、规划，也可做受限选择 |
| 本项目实测 | 未部署、未测速 | L4 / CUDA，逐项决策 | Bedrock Converse，reasoning `low` |

BERT 本身属于深度学习。基于 BERT 的文本对或 NLI 蕴含模型也能按候选描述评分，支持动态候选或零样本分类；动态候选并非 Decider 独有。没有 BERT 的实测数据，不能根据 Decider 快于 GPT 的样例推断 Decider 比 BERT 更快或更准确。

## 演示参考不等于执行规则

| 代码入口 | 职责 |
| --- | --- |
| `app/crypto.py::OPTIONS` | 提供候选动作和适用条件 |
| `facts()` / `payload_for()` | 计算已知事实并构造模型输入 |
| `reference()` | 用开发者定义的策略计算演示参考，用于对照 |
| `execution_action()` / `apply()` | 根据执行时的实际条件校验资金与结案，记录实际动作 |
| `app/crypto_loop.py::tick()` | 读取执行结果，将反馈用于下一轮判断、等待或重判 |

参考选择在模型输出之后独立比较，不直接填入模型输入作为答案。原始选择与参考不同只记录差异；应用允许合理的保守路径继续处理，但仍可能挂起资金。执行保护调整不能计作模型预测正确。

默认 12 次确认、60 分钟结算 SLA 是演示参数，不是行业统一标准。金额、地址、权限、记账与幂等应由支付系统执行。模型的价值主要在自然语言理解与路径选择。

## 固定流程与反馈闭环

- **固定流程**：冻结本轮输入，每步并发比较 Strands Decider、Jev、GPT 三模型，收齐建议后执行各自方案。同一输入指纹且均成功的结果才进入配对速度统计。
- **优化流程**：保持固定流程的候选 ID、证据与执行保护，按场景去除无关字段、明确候选适用条件。四个场景均支持；非退款不再携带退款审批字段，商户结算不再携带收款确认字段。三模型使用相同优化输入，原始选择与实际执行仍分别记录；不能把输入优化等同于模型微调或保证准确率。见 [具体字段与候选定义](../app/crypto_profiles.py)。
- **反馈闭环**：每侧独立地判断、执行并读取结果，外部条件缺失时等待事件，无效动作可有限重判。各模型后续输入可能不同，重点看业务是否完成、调用数、无进展和人工接管。
- **完成口径**：决策返回、步骤处理、资金动作和业务完成分别显示。只有目标订单、对应模拟账本和工单结案均确认，才显示完成。
- **输出来源**：模型选择、应用实际动作、模拟器事件和客服模板分别标记；失败请求不会被规则回放替代。

当前 [30 页 v8 演示资料](presentations/v8/README.md) 展示三模型预热实测、逐步输入输出、JevBench 与优化方法。另行保存的 USDC 闭环中，三侧各六次决策、一次模拟确认事件后均完成；Decider 首次核验误选也完整保留，见 [闭环说明](CLOSED_LOOP.md)。固定输入优化的前后对照为 Decider 14/20 → 18/20，模型权重未变；原始样本与历史部署观测见 [项目历史](HISTORY.md)。
