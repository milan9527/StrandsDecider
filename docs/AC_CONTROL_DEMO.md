# 空调控制三模型实时演示

入口：[空调控制对比](https://d3i7ogfx5ml7dc.cloudfront.net/#ac-control)，登录后使用。

Liquid LoRA、Jev 与 GPT 6.1 Sol low 使用相同的业务输入、问题、候选顺序和参考答案，展示实际选择、逐字段差异及耗时。参考答案仅用于展示和评分，不发送给模型。演示生成控制命令，不连接真实空调。

从新建 GPU 实例开始部署和训练，见 [Liquid 从 EC2 部署到 LoRA 微调完整手册](LIQUID_LORA_EC2_HANDBOOK.md)，包含环境、训练、评估、服务发布及本演示的接入步骤。

## 场景与调用方式

沿用 [AC_Control_Test_Spec.md](../validation/ac_control/runs/2026-10-30-v1/spec.md) 和本次 LoRA 回归的冻结输入：原规范 20 题、中文表达 24 题、英文改写 24 题、扩展诊断 10 题；共 78 个场景、30 项能力、283 个候选。保留完整能力表、原问题指令及 omit 条件，支持原序与倒序对照。

| 概念 | 页面中的含义 | 示例 |
|---|---|---|
| 单指令 | 用户请求一种设置，不代表只需要一个输出字段 | 设置 24℃，需要温度和温标两个字段 |
| 多指令 | 同一条指令包含多个设置要求 | 开机、制冷、设置温度和风速 |
| 单步决策 | 一次请求只判断选定的一个字段 | 只判断 `t_power`；准确率只评价这个字段 |
| 30 步串行 | 同一条用户指令依次提交 30 次单字段请求 | 每步保留完整状态；上一字段答案不传入下一步 |
| 一次全答 | 一个请求携带全部 30 个问题 | 每个字段返回合法候选；未要求修改的字段返回 omit |

“三种方式对比”分别运行单步、30 步串行、一次全答，每个场景共 96 次实际模型调用。各模型和各请求依次执行。“运行全部规范场景”固定执行原规范 20 条，沿用当前调用方式、单步字段和候选顺序；一次全答为 60 次调用，三种方式全测为 1,920 次调用。页面可取消尚未发出的请求，当前调用结束后停止。

## 看结果

三个模型分别显示选出的命令、是否完全正确、字段符合数量及任务耗时。展开明细可查看每个问题的完整选项、参考选择、模型实际选择、原始响应和输入 SHA-256。差异分为多发、漏发、错值及未返回；关闭值 `0` 是实际命令，与 omit 不同。

单步按所选字段判分；串行及一次全答要求 30 字段全部正确。接口失败单列并保留在已完成任务的准确率分母中；取消任务不计入正确率。服务不会自动重试、改答案、补 omit 或切换模型。

任务耗时从后端开始处理该模型任务算起，包含模型请求、网络和服务端等待。串行总耗时覆盖全部 30 次调用，明细保留每次往返；一次全答的字段明细显示整请求耗时，不能再把它乘以 30。“本轮等待”还包含其他模型的运行时间。页面历史参考来自既有报告，实时结果由本轮调用产生；托管服务路径、网络和冷启动会影响延迟。

JSON 导出包含运行配置、实际响应、评分、时间、输入哈希和完整输入。`model_input_json` 保留请求中候选键的实际顺序；JavaScript 会重排整数形式的对象键，因此核验倒序请求时应使用这个字符串字段，而不是重新序列化 `model_inputs`。单步输入可按回执的 `keys` 从完整输入提取，保持 state 与候选顺序。

运行中刷新页面可恢复查询。后端仅保留最近 5 轮任务，新建任务时清理超过 2 小时的记录；API 重启会清空内存记录，需及时导出。同一时刻只接受一轮空调对比。

## 模型与维护

- **Liquid LoRA**：`LiquidAI/d1-2B`，本次 `adapter-1024.pt`；BF16 合并权重及官方原生推理路径。适配器 SHA-256：`2a87384a624545021fc6ca91cf5406ed42e518a8607f048ca264048f57a0d171`。启动时核验基础权重、适配器及冻结推理脚本，业务接口校验返回的模型和适配器身份。
- **Jev**：沿用现有 Lambda 转发，使用 `jev-latest`，实际返回版本保存在每次响应中；输入校验扩展到 30 问及每问最多 102 个候选。
- **GPT**：沿用 Bedrock Converse 的 `us.openai.gpt-6.1-sol`，`reasoning.effort=low`，输出上限 8,192 tokens，系统提示词与此前空调统一测试一致。

场景快照：[app/ac_control_cases.json](../app/ac_control_cases.json)；调度与评分：[app/ac_control.py](../app/ac_control.py)；前端：[ac-control.js](../frontend/static/ac-control.js)。

Liquid 服务复用 `us-east-1` 的现有 `g6.xlarge` / L4 实例，未新增或停止 EC2。模型由 `ac-liquid-lora-model.service` 管理，仅监听本机 18821；认证网关由 `ac-liquid-lora-demo.service` 管理，18125 端口仅向业务 API 安全组开放。

API 通过 CloudFormation 参数 `AcLoraUrl`、`AcLoraSecretArn` 注入 `AC_LORA_URL` 和 `AC_LORA_TOKEN`；密钥由 Secrets Manager 保存，不进入前端。后续部署脚本保留这两个已配置参数；首次接入其他环境时，还需配置私网路由、安全组和实例端服务。模板辅助代码见 [ac_control_infrastructure.py](../deployment/ac_control_infrastructure.py)，服务源码见 [ac_lora_server.py](../deployment/open_models/ac_lora_server.py) 与 [ac_lora_gateway.py](../deployment/open_models/ac_lora_gateway.py)。

共 **261 次真实模型调用，接口异常 0 次**，每次均核对输入哈希、评分和耗时。包括原规范 20 题一次全答、S01 / M09 三种调用方式、M09 / 一个中文场景倒序全答，以及在真实浏览器新发起的 M08 对比。桌面和手机浏览器验证运行、进度查询、结果恢复、完整倒序选项、错误明细及导出通过，无 JavaScript 错误；导出响应与后端记录一致。

原规范 20 题一次全答，每题运行一轮：

| Liquid LoRA | 18/20 | 0.756 秒 |
