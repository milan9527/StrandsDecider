# Decider vLLM：并发与批次预算测试总结

[English](VLLM_PERFORMANCE.md) | 简体中文

本文汇总 **2026-10-13** 的 Decider vLLM 自身测试：原版串行服务对比、并发复测、1–128 并发扫描，以及更大批次 token 预算。两种公网服务的对比另见 [Decider vLLM 与 Jev 性能报告](JEV_CONCURRENCY.zh-CN.md)。

**对这批短决策输入，单张 NVIDIA L4 可从 4–8 并发开始配置。** 独立 1–128 扫描在 8 并发测得最高吞吐 33.84 次/秒；继续提高并发主要增加延迟。批次 token 预算从 8192 提高到 16384、32768，没有带来吞吐提升，因此部署仍保留 **8192**。

## 测试数字的含义

| 指标 / 参数 | 本次含义 |
|---|---|
| 一次请求 | 对一个业务步骤进行一次判断，不是一笔完整支付流程 |
| 客户端并发 | 等待响应的 worker 数；每个完成后立即补发下一条 |
| 次/秒（RPS） | 成功完成的决策请求数 / 正式测量总耗时 |
| 延迟 | 客户端 HTTP 往返时间，包含网络、排队和处理 |
| P95 / P99 | 成功响应的 nearest-rank 分位数；失败仍影响吞吐并单独计数 |
| `max_num_seqs` | 引擎序列上限，不保证所有已接收请求在同一批执行 |
| `max_num_batched_tokens` | 每批调度 token 总预算，不是请求数或单条输入长度 |

共同语料来自四个支付场景 × 五个独立步骤，共 **20 条固定输入**，每请求一个选择题。完整输入包含业务事实、指令、候选项及条件，长度 **304–445 tokens，平均 373.9**。Decider 的 `output_tokens=1` 表示一个决策，返回 JSON 由适配器组装，不是逐 token 生成。各步骤之间不推进业务状态。

预热单独记录，不计入性能数据。客户端复用 HTTP 连接，失败不自动重试。重复输入用于观察性能与适配一致性，不能当作数千个独立的业务准确率样本。

## 测试批次与证据

每行是一轮独立实验。硬件路径、限额、样本数存在差异，不合并统计。

| 实验 | 环境 / 目的 | Decider vLLM 正式请求 | 主要观测 |
|---|---|---:|---|
| [原版与 vLLM 对比](GPU_CONCURRENCY.zh-CN.md) | 同一 g6.4xlarge / L4 主机；推理容器限制 4 vCPU / 14 GiB；回环 HTTP | 三轮 vLLM 共成功 2555/2560 | 8 并发的完整复测为 34.91 次/秒，原版为 14.76；其他轮次保留五次超时 |
| [HTTP 清理修复后复测](CONCURRENCY_RETEST.zh-CN.md) | g6.xlarge / L4；公网 HTTPS；引擎上限分别为 8、32 | 5200/5200 成功，数值对齐全部通过 | 16/32 并发均完成；8 并发延长复测为 33.32 次/秒 |
| [1–128 并发测试](CONCURRENCY_128.zh-CN.md) | g6.xlarge / L4；公网 HTTPS；引擎 128，HTTP / 问题准入 256，批次预算 8192 | 12800/12800 成功，含 64/128 复测 | 扫描最高为 8 并发的 33.84 次/秒；一次置信度差异超阈值 |
| [8192/16384/32768 批次预算](BATCH_TOKENS.zh-CN.md) | 同一公网部署，只改变批次 token 预算参数 | 23040/23040 成功，数值对齐全部通过 | 未提升吞吐；更大预算下，128 并发 P95 反而增加 |

原版对比的收益包含权重合并、不同内核、线程设置和调度变化，不能全部归因于批处理。HTTP 清理修复后完成了成功复测，但并未证明所有历史超时都由同一原因导致。

## 独立 1–128 并发扫描

下表完整来自 [独立扫描批次](results/concurrency-1-128-2026-10-13/sweep-1-128/benchmark.json)，**每档正式请求 1280 次**，20 条输入各重复 64 次。表内请求全部成功。

| 并发 | 次/秒 | 平均 ms | P95 ms | P99 ms |
|---:|---:|---:|---:|---:|
| 1 | 18.10 | 55.1 | 59.9 | 63.7 |
| 2 | 22.85 | 87.4 | 89.9 | 91.7 |
| 4 | 33.11 | 120.6 | 131.8 | 135.2 |
| 8 | 33.84 | 236.0 | 245.0 | 247.0 |
| 16 | 29.34 | 544.4 | 561.8 | 572.7 |
| 32 | 30.06 | 1057.9 | 1089.9 | 1103.5 |
| 64 | 29.76 | 2112.7 | 2178.7 | 2822.1 |
| 128 | 29.65 | 4111.9 | 4986.1 | 7568.0 |

另外进行的 128 并发复测为 **29.65 次/秒，P95 5018.0 ms**。允许更多请求同时进入，没有带来同比例的处理能力增长。

首轮 128 并发中，一次 `underpaid/approve` 仍选择 `approved`，但置信度从 0.5917 变为 0.6119，差值 **0.0202** 超过未修改的 **0.02** 阈值。因此数值对齐为 **12799/12800**，与 HTTP 成功率分开统计。

## 更大批次 token 预算

下表使用 [批次预算实验自身重新采集的基线](results/batch-tokens-2026-10-13/summary.json)，没有复用上面的扫描数据。除 `max_num_batched_tokens` 外，其他配置一致；每格均包含 1280 次成功请求。

每格为 **次/秒 / P95 毫秒**。

| 并发 | 8192 tokens | 16384 tokens | 32768 tokens |
|---:|---:|---:|---:|
| 8 | 37.01 / 231.0 | 33.67 / 242.7 | 34.27 / 242.2 |
| 16 | 30.55 / 546.1 | 30.50 / 547.7 | 30.71 / 535.0 |
| 32 | 30.34 / 1069.5 | 29.94 / 1081.9 | 29.78 / 1087.2 |
| 64 | 30.20 / 2137.2 | 29.75 / 2189.4 | 29.67 / 2200.0 |
| 128 | 29.92 / 4932.3 | 29.61 / 5166.7 | 29.44 / 5983.9 |

32768 预算的 128 并发复测为 **29.23 次/秒，P95 5903.6 ms**。23040 次总量包含 32、64、128 并发的独立复测，数值对齐全部通过。

32768 已能容纳 64 条当前最长输入（`64 × 445 = 28480`），64 并发仍约 30 次/秒。提高预算上限不会强制形成更大实际批次，也不会增加 GPU 算力。本轮没有定位具体的内核、CPU 环节或网络瓶颈；单次运行之间的小幅变化不应当作已确认的调参效果。

## 当前配置与结论适用范围

公网服务保持批次预算 **8192**、引擎序列上限 **128**、HTTP / 问题准入 **256**。这些是准入和调度上限，不是推荐同时施加的负载，也不是吞吐保证。每秒 2000 次的速率阈值同样不代表 GPU 实测吞吐。配置见 [部署记录](DEPLOYED.zh-CN.md)。

对于当前语料，可从 **4–8 并发**开始，结合延迟目标和失败率选择实际负载。候选 ID 一致与概率、置信度对齐应分别检查。模型仍为 BF16 底座和原始 FP32 Pointer Head；压测没有训练或优化模型权重。

后续 [Jev 对比](JEV_CONCURRENCY.zh-CN.md) 保留了一次 Decider HTTP 502，以及十次置信度差 0.0202。该轮 Decider 在 128 并发的客户端 P95 为 11236.8 ms，服务端自报 P95 为 187.1 ms，大量耗时位于服务端计时范围之外，具体来源尚未定位。这组观测与独立扫描分开记录，也说明不能用一个汇总数字判断高并发尾部延迟或硬件是否达到极限。

继续调优应先分析实际批次大小，以及客户端传输、请求处理、CPU 预处理、调度、GPU 内核分别耗时多少。CUDA Graphs 需要适配验证；当前实现要求完整 prefill，不能直接开启前缀缓存和分块预填充。长上下文、多问题请求、持续到达负载及多副本需要单独测试。

每轮报告都链接原始请求、预热、数值审计、启动参数和 SHA-256 清单。[验证记录](VALIDATION.zh-CN.md) 汇总检查与异常；独立的 [Jev 报告](JEV_CONCURRENCY.zh-CN.md) 说明两种服务的性能差异。
