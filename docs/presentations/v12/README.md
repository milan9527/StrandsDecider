## 实测结论

2026-10-15，四场景 × 两种输入 × 三个模型 × 五步，共 **120 次正式调用，全部成功**。另有 6 次预热，不计入统计。

| 模型 | 原始 → 优化：与演示参考一致 | 原始 → 优化：平均后端耗时 |
|---|---:|---:|
| Strands Decider | 14/20 → 18/20 | 86.2 → 91.5 ms |
| Jev | 18/20 → 20/20 | 394.9 → 388.5 ms |
| GPT-6.1 Sol · low effort | 20/20 → 20/20 | 1414.3 → 1271.9 ms |

优化的是输入字段、候选条件与阶段说明，模型权重未变。原始 `approved` 条件已有“其他场景无需退款审批”的说明；优化把适用范围也明确写到其他候选，并删除不适用字段，减少条件之间的歧义。不能把本次效果单独归因于删掉某个字段或增加某一句话。

普通收款审批中，Decider / Jev 从 `await_approval` 改为 `approved`，执行状态 `review_pending` 从 `true` 变为 `false`。三者仍等待链上 3/12 确认，未入账、未结案。**消除多余审批不等于完成收款。**

优化后 Decider 仍有两项错误：少付核验选择等待确认，退款地址未验证却选择批准。其中少付核验由原来的正确选择退化；另一个执行节点改善，因此该场景总分仍为 4/5。退款的执行器纠正单独记录，不能算作模型选择正确。

## 采集与数据口径

- 使用在线演示的真实模型接口。Decider 为现有 `g6.xlarge` 上的官方原版服务，模型 `strands-decider-2B-hobson-v19`；Jev 返回 `jev-1.13.0`；GPT 为 `us.openai.gpt-6.1-sol`，low effort。
- 同一个场景先跑原始输入，再跑优化输入；每阶段三模型并行、五阶段顺序执行。三模型获得同一 `model_input`，供应商 API 封装不同。
- 固定流程使用冻结业务快照，每阶段更换问题与候选；不把执行后的状态反馈给下一次模型请求。持续调整的闭环仍在第 14 页单独说明。
- 每种组合仅测一次，未随机化顺序。耗时取 `timings.backend_total_ms`，包含应用排队和提供方调用，不是纯 GPU 时间或浏览器 RTT。**本次验证选择改善，不据此宣称稳定加速。**
- 一致性以模型原始 `choice` 对照业务代码生成的演示参考；参考答案不放入模型输入。该比例不是行业准确率。
- 全部资金与客服动作在演示沙盒执行，没有外部资金操作。四个初始场景都有尚未满足的业务条件，五步跑完也不意味着资金完成。
- 第 14 页及后续验证、vLLM、成本保留原数据口径；本批支付数据没有替代成本图使用的 Jev token usage 样本。
