## 03. 原理：从文本生成头，切换到候选项评分头

## 04. 一个 choice 判断，怎样从输入变成输出？

prompting.py把state、instructions、带编号的候选名称与描述组织为文本，最后是<answer>。模型主体读取文本，PointerHead从<answer>位置取query，从每个候选描述末token的位置取key。LayerNorm后经可学习投影得到q、k，点积除以sqrt(pointer_dim)得到各候选logit。按问题类型使用温度T，再在有效候选上做softmax；choice取最大概率对应候选。choice的confidence是归一化最大概率，不是另一次推理，也不是自然语言解释。K>1时为clip((K*p_max-1)/(K-1),0,1)，K=1时为1；score使用另一套有序分布统计，不能套此公式。单个choice直接评分；多问题可共享前缀缓存或批处理。本项目五个步骤分别发起调用，绝非整条业务流程只有一次前向。

## 07. 与 BERT 分类器的关键区别：标签含义放在哪里？

常见BERT监督分类器以[CLS]的池化表示作为输入，分类头W具有K个输出维度，对应预先定义的K个类别。输出维度的语义来自标签映射和监督训练；不是每次调用都通过自然语言给这些维度重新赋义。Decider的候选名称和适用条件随请求输入。PointerHead对每个候选位置使用共享的q/k投影，头的参数量不随K增长。候选数量仍受上下文长度和计算资源限制，不能理解为无限输入。两者都可直接做非自回归的分类评分，不必生成长文本。

## 08. BERT 与 Decider：任务适配方式不同，需按业务实测

BERT也可构造成文本对或NLI蕴含模型，逐个候选评分，实现动态候选或零样本分类；那不是这里比较的固定K类分类头。BERT-base约110M参数，Decider约2B；本项目没有部署或测试BERT，不能用Decider快于GPT的结果推导Decider快于BERT。固定标签、充足领域标注与大量请求时，应评估BERT等紧凑分类器；候选经常变化、希望以自然语言定义任务时可评估Decider。二者都可能违反业务约束，概率和阈值均应在业务域校准。新增候选无需扩头不意味着新任务能可靠零样本泛化。

## 15. 什么是“演示参考”？它是开发者写出的业务基准

OPTIONS提供候选动作与适用条件，facts计算金额差额、足额、确认数等结构化事实，payload_for把这些事实与条件发给两模型。reference(s,stage)以确定性Python分支计算一个预期动作；matches_reference只是原始choice与这个动作是否相同。execution_action是另一层保护：检查实际执行时的资金条件与结案状态。普通支付没有risk_flag即可通过本阶段风控检查，是否已经足额并达到确认数是资金执行阶段再检查的条件。审批规则检查通过不等于立刻收款。参考不来自Decider或GPT，也不是行业统一标准。
