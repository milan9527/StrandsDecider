# 空调控制五模型对照测试总结

测试日期：2026-10-30。依据 [AC_Control_Test_Spec.md](AC_Control_Test_Spec.md)，比较 **Strands Decider、Liquid、H2O、Jev、GPT 6.1 Sol low** 根据英文请求选择空调控制 Key / Value 的能力，并验证提示词澄清及两阶段选择是否有帮助。

**本批原规范20题中，GPT基线已全部正确；Jev从19/20提升至20/20，只需澄清规则。H2O和Liquid受益于两阶段，但存在诊断题回归或漏选；Decider的四种改写均未超过基线。** 结果支持按模型选择提示与流程，不能把“增加说明”或“拆成两步”视为普遍有效的优化。

本次仅调用模型推理，没有向真实空调下发控制。下文“正确”指完整指令集合与规范参考一致，不是只要选中了某个正确选项就通过。

## 1. 测试范围与比较方式

| 项目 | 本次设置 |
|---|---|
| 主测试集 | 规范20条英文Query：单指令10条、多指令10条 |
| 换序检查 | 同20题反转每题候选顺序，检查输出是否改变 |
| 诊断集 | 另10条新表达与反例，只测原始候选顺序，单独计分 |
| 能力范围 | 每次携带相同的完整30项Command Set |
| 基本输出 | 每个Key一个choice，选择合法Value或`omit` |
| 数值候选 | 枚举整个合法整数范围，例如DR Load为0–100加`omit`，共102项 |
| 每模型观察数 | 20题 × 2种顺序 × 5种方案 + 10题 × 5种方案 = 250条 |
| 合计 | 五模型共1,250条观察；相同题目重复测试，不是1,250道独立题 |
| 参考与评分 | 参考答案只用于离线评分，不发送给模型，不修复模型答案 |

`omit`表示不下发该Key；`0`是实际控制值，不能把二者等同。摄氏设温须同时输出`t_temp`和`t_temp_type=0`，华氏设温须同时输出`t_temp_f`和`t_temp_type=1`。输出多余、缺失或错误指令均判整题失败。

### 五种对照方案

| 方案 | 改动 |
|---|---|
| 原始基线 | 保留最初的规则、问题说明与候选描述 |
| 仅改选项条件 | 将候选描述改成明确的适用条件；候选ID、合法范围和顺序保持一致 |
| 仅改规则与问题 | 明确能力目录不等于用户请求、温标伴随字段、独立功能与摆风编码的区别 |
| 两项合并 | 同时采用上述两种改写 |
| 两阶段 | 在合并改写基础上，先对全部30个Key选`apply/omit`，再对模型选中的Key选Value |

两阶段的第二步仍允许`omit`，以便撤销第一步的多选；但第一步漏掉的Key无法由第二步补回。两个阶段都保留完整能力集；第一步全部选`omit`时不调用第二步。

## 4. 一个具体错误：摆风重复编码

M08原始请求：

> Turn on up-and-down swing and set the horizontal airflow to both sides.

含义：开启上下摆风，并将水平送风设为两侧。规范要求：

```json
[
  {"cmdKey": "t_up_down", "cmdValue": "1"},
  {"cmdKey": "t_swing_direction", "cmdValue": "2"}
]
```

Jev基线实际多输出了一条：

```json
[
  {"cmdKey": "t_up_down", "cmdValue": "1"},
  {"cmdKey": "t_swing_angle", "cmdValue": "0"},
  {"cmdKey": "t_swing_direction", "cmdValue": "2"}
]
```

`t_up_down=1`与`t_swing_angle=0`都可以表达上下摆风，但规范要求使用专门的上下摆风Key，不能重复下发。规则改写明确说明：

> When both vertical swing keys are available, a request to enable or disable continuous vertical swing uses t_up_down only; do not additionally emit t_swing_angle=0 for the same request. Fixed vertical positions use t_swing_angle.

加上这条区别后，Jev正确；GPT基线本身正确；H2O仅改规则与两阶段正确，合并改写仍重复编码。这里确有可澄清的协议语义，但不同模型对同一澄清的响应不同。

### 单任务串行与单Key串行的补测

对原始运行记录的复核确认：三个GPU模型各210条新增观察的请求时间无重叠，三个模型的运行区间也无重叠。测试脚本按 **Decider → Liquid → H2O** 顺序执行，每条空调Query返回后才发下一条。多模型常驻显存不等于同时向多个模型发起推理；这些记录不能排除共享服务的其他外部访问，但GPU测试没有并发发压。Jev与GPT各自串行，两路独立API曾同时运行；它们在GPU测试结束后才开始，不占用本地L4。

需要区分两个层级：**一条空调Query包含30个Key选择题。** Decider适配层会为每个Key创建独立引擎任务；H2O本轮使用双向注意力模式，逐题处理state，不能使用其因果模式的前缀缓存。S03基线中，Decider报告处理39,778个输入token；H2O报告输入6,468个token、实际处理40,137个token。后者显式区分了业务输入与重复处理量。Liquid的原生接口则支持把多个问题一起处理。GPT通过一次生成回答全部Key。因此原表适合比较当前接口方案完成整条控制请求的耗时，不是同硬件下单次选择的模型速度排名。

进一步使用**同一个S03基线请求**补测五个模型：先完成Decider、Liquid、H2O，再按相同标准新增Jev、GPT；业务输入逐字节相同，每模型预热一次，各模式重复3次并交替顺序。新增API测试在同一进程中先完成Jev，再开始GPT。逐Key模式每次只发送一个问题，收到结果才发下一个，但每次仍携带相同完整30项能力集与原有候选。GPT继续使用原固定格式提示、8192 token上限及low effort。

“单步决策”指**一次请求回答一个Key**；“30步串行总时间”指首步开始至第30步返回，包含中间记录开销；“一次回答30题”则是一条请求中完成全部Key选择。这里的单步不是两阶段方案中的门控阶段。

| 模型 | 实测单步均值 | 单步P95 | 30步串行总时间均值 | 一次回答30题均值 |
|---|---:|---:|---:|---:|
| Strands Decider | 97.3 ms | 116.7 ms | 2,925.2 ms | 2,878.8 ms |
| Liquid d1-2B | 105.8 ms | 115.8 ms | 3,179.2 ms | 611.6 ms |
| H2O Lightning 4B | 200.5 ms | 244.3 ms | 6,019.1 ms | 5,887.6 ms |
| Jev 1.14.0 | **55.6 ms** | 82.7 ms | **1,679.9 ms** | **108.1 ms** |
| GPT 6.1 Sol low | **902.3 ms** | 1,322.8 ms | **27,084.9 ms** | **2,308.6 ms** |

独立单Key均值来自每模型90次实际单题请求，不是将原30题请求耗时直接除以30。完整请求与30步串行总时间各统计3轮。本轮Jev/GPT新增186次正式调用、2次预热；加上前三模型已保存的279次正式调用、3次预热，共465次正式调用、5次预热，全部响应有效。保存的所有请求及五个模型测试区间均无重叠，无自动重试或采集缺失。此前五组提示词实验中的API并行情况属于旧实验，本补测按模型依次执行。

这次单步比较中，三个GPU决策模型均快于GPT。Jev和GPT一次回答30题的耗时也远小于各自调用30次：拆成30步后，Jev总时间约为一次全答的15.5倍，GPT约为11.7倍。不能根据完整30题请求的耗时，推断一次独立选择的速度；本场景一次提交完整问题能明显缩短总体等待时间。

补测说明：Decider和H2O单题选择是约百毫秒量级，处理完整30题后累计到数秒；Liquid批量处理更快，强制逐Key串行反而增加总耗时。H2O当前部署还使用单张L4、`--max-num-seqs 1`及eager执行；这些是已核对的部署条件，尚未通过逐项实验分离各自的性能影响。GPT托管硬件、引擎和缓存条件不同，也不能仅根据模型参数量推断端到端时间。

GPT返回的单Key服务端平均延迟为892.8 ms，接近客户端902.3 ms；两者相差约9.6 ms，主要耗时位于服务端路径内，但该字段不能进一步分离推理、排队和内部调度。3次完整请求均报告缓存读取，90次单Key请求中71次报告缓存读取；未显式配置缓存，不将这一结果解释为无缓存性能。Jev未返回服务端耗时。GPU测试从GPU主机走loopback，Jev/GPT沿用原API测试主机分别走HTTPS和Bedrock；客户端、模型硬件、网络及服务条件不同，这仍是接口方案实测。

两种调用方式的质量结果也不能直接混用：S03中Decider与H2O的选择未变，Liquid每轮均有6个Key发生变化。新增Jev与GPT各3轮拆分前后均无Key变化，均选择 `t_temp=24`、`t_temp_type=0`，其余28个Key为 `omit`；两个模型×两种模式×3轮的12份完整结果均符合S03参考，见[本场景离线核验](../validation/ac_control/runs/2026-10-30-api-serial-latency-v1/case_check.json)。原正确率表仍表示“完整30题请求”这一固定封装的结果；本次只做一道Query的延迟与输出一致性诊断，没有据此重写原20题成绩。

## 6. 采集异常、证据完整性与复核

新增Jev/GPT测试共500条正式观察、600次调用尝试；预检独立保存，不计成绩。Jev的250条均有完整响应。GPT前179条保存成功，第180条在序列化SDK对象时遇到bytes字段，进程在写入记录前退出。

该条为 **M08 / reversed / criteria_only**。原始回答、返回状态和耗时均未保存，无法恢复，也无法确定模型是否答对。因此：

1. 将该条记为`capture_error`，保留在准确率分母中，按失败计；不把它解释为模型输出了空指令或错误答案。
2. 保留原日志、前179条响应及中断时元数据，不覆盖原记录。
3. 只增加SDK bytes字段的无损Base64保存，继续尚未调用的后70条；未重跑缺失题，未更改提示、模型、low参数或评分。
4. 最终499条新增观察有完整返回证据；这1条采集缺口明确写入报告与核验文件。原始顺序主结果不受影响。

**优先采用本批已验证的简单方案。** Jev可优先验证“仅改规则与问题”；GPT可保留基线，作为后续更难测试的质量参照。两者在本批20题及10条诊断题均达到满分，不足以据此判断更广泛请求上的可靠性差异。

**H2O和Liquid需要结合漏选与回归评估。** 两阶段确有主测试收益，但H2O诊断题出现回归，Liquid仍有9道主测试题不完全正确。上线选择不能只依据20题主表。

**Decider不宜继续仅靠叠加长提示来解决当前任务。** 可另行评估更合适的任务拆分或领域训练，并使用未参与优化的测试集验证；本轮数据不能证明这些方案一定有效。

**协议约束应明确，工程校验应与模型评分分开。** 温标伴随字段、`omit`与`0`、摆风等价编码、独立功能与主模式的区别，适合写成清晰规则。未来若在工程层补单位、检查范围或拦截互斥指令，应同时保留模型原始输出与最终执行结果，不能用修正后的答案覆盖模型成绩。
