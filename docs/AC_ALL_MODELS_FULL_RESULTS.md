## 过程与统一口径

| 项目 | 每模型实际覆盖 |
|---|---|
| 规范主成绩 | 原序 20 条完整请求各一次：单指令 10、多指令 10，共 40 个预期命令对 |
| 质量附项 | 同 20 题反序；10 条英文诊断、24 条英文新题、24 条中文翻译，各含原序与反序 |
| 单步决策 | 20 Query × 30 Key × 3 轮，共 1,800 次实际单字段请求 |
| 30 步串行 | 上述请求每 30 步组成一个完整任务，共 60 个任务 |
| 一次全答 | 相同 20 Query × 3 轮，每请求回答完整 30 字段，共 60 个任务 |
| 预热 | 3 次 S03 全答；质量请求之后，对 S03 的 30 种字段形状各预热一次 |
| 合计 | 2,049 次：2,016 正式、33 预热；九模型共 18,441 次 |

冻结业务输入、选项及调用顺序后才开始推理。按 Jev→GPT→Strands→Liquid→Perplexity→KnowLine→Torchcast→Clef→H2O 依次运行，所有外部请求串行；每个模型的 156 次质量请求和布局顺序相同。按题号与轮次交替串行/全答的先后次序，保留服务原生缓存。逐字段时每次保留完整状态、能力表和该字段的全部选项，不把上一字段的回答传入下一字段。

30 步总时间由实际整轮墙钟测量，计时结束后才写盘或上传证据。字段调用时间使用每次客户端往返，完整请求时间同样包含服务及网络开销。七个本地模型使用独占 g6.xlarge/L4 原生服务，Jev/GPT 使用托管 API；统一任务与流程不等于统一托管硬件。所有原始选择保留，只移除 omit、补展示用 cmdName，不补单位、不删除额外命令，不向真实设备执行控制。

整个测试脚本还要执行质量附项、预热和证据上传，运行时长远大于一条业务指令的延迟。逐模型的脚本墙钟时间与全部请求计时之和另存于 `summary.json` 的 `run_timing`，不用于替代下方三种请求方式的响应时间。

GPT 固定 `us.openai.gpt-6.1-sol`、每请求显式 low effort、8192 输出 token 上限；系统提示只约束读取输入和 JSON 输出格式。Jev 以首个成功预热的返回版本锁定整轮。

## 机制、结论与对照边界

一个完整请求的内部计算方式因服务而异：Strands 与 H2O 分字段创建评分任务；Liquid、Perplexity 和 Clef 有原生多问题处理路径；KnowLine 每题前向，完整请求先预热共享前缀，再通过 16 个线程提交评分，且按整请求长度决定是否重复输入；Torchcast 大候选集合采用分组选择，完整多字段可能走不同图执行路径。GPT 一次生成全部字段的 JSON；Jev 内部硬件、算法及缓存明细未由调用记录揭示。具体机制见[此前模型差异说明](AC_SPEC_UNIFIED_RESULTS.md#model-differences)和[固定版本候选资料](AC_MODEL_CANDIDATES.md)。这些资料解释实现差异，本轮时间与准确率以上方新实测为准。

**Strands 的主要问题是漏动作。** 1,800 次单字段请求中，有 63 次将应执行字段选为 omit，另有 3 次多发。串行整组为 12/60（20.0%），全答为 12/60（20.0%）；60 组可比较任务中有 0 组选择发生变化。当前基线的语义错误没有通过拆分问题得到解决。

**Liquid 的主要问题是多发动作。** 单字段模式选对了全部必要动作，但额外下发 330 个未请求字段；串行仅 M09 存在完整答对的轮次，合计 3/60（5.0%）。全答为 0/60（0.0%）。串行与全答的字段错误分布不同，不能把拆分本身当作可靠的准确率优化。

**Perplexity 对请求方式尤其敏感。** 串行整组为 60/60（100.0%），全答为 3/60（5.0%）；串行平均 10.684 秒，全答 1.513 秒。本轮支持继续验证其逐字段方案，但不能据此采用其全答方案。扩展题本轮只测了全答，尚不能将规范题上的串行表现推广到所有新表达。这些结果证明当前部署受请求布局影响，未单独隔离提示上下文、内部批处理和数值路径，因此不能把全部差异归因于其中一个因素。

**KnowLine 的串行方式也提高了本轮规范正确率，但需要更长时间。** 串行为 57/60（95.0%）、6.559 秒；全答为 54/60（90.0%）、1.007 秒。串行修复 S04 多发摄氏温度的错误，M08 多发摆风角度的错误仍存在。本轮 S03 单步均值也为 221.3 ms，高于旧七模型仅重复 S03 时的 100.8 ms；因此差异不只是汇总了更多题目。两轮的请求历史、缓存状态与测试实例不同，本轮没有单独隔离这些因素的贡献，不能把历史延迟直接替换进当前对照。

**KnowLine 的两种布局实际触发了不同的内部提示策略。** 官方阈值统计“共享前缀一次 + 所有问题行”的 token 数，超过 3,000 就关闭 read-twice。本批 20 个全答形状为 6,558–6,580 token，均只读一次；600 个单字段形状为 1,256–2,352 token，均将输入重复两遍后进行一次评分前向。这不是 apply/omit→Value 的两阶段决策，也不是客户端额外发出一次请求。以部署相同版本的 tokenizer 和官方源码离线重建后，三轮全部 1,860 次布局请求的评分输入 token 数都与实际响应一致，没有新增模型推理。S04 的 `t_temp` 在全答中被选为 20，在单字段中为 omit；该字段的内部提示确实不同。read-twice、内部调度与缓存同时随布局变化，本轮未做单因素消融，不能声称准确率变化完全由 read-twice 造成。完整输入文本、阈值计数与逐条核对见[源码重建证据](../validation/ac_control/runs/2026-10-30-all-models-full-v1/knowline-layout-analysis.json)。

**Torchcast 合并请求后没有提速。** 串行整组为 54/60（90.0%）、平均 10.839 秒；全答为 54/60（90.0%）、平均 12.459 秒。两种方式都在 M07 多发一键自清洁、在 M08 多发摆风角度，三轮结果一致。一次外部请求不意味着内部只做一次计算；其多字段与大候选处理路径的实际耗时需要测量，不能按减少 HTTP 次数推算速度。

**Clef 串行修复了 M08，但需要更长时间。** 单字段为 1800/1800（100.0%），串行整组为 60/60（100.0%）、平均 14.664 秒；全答为 57/60（95.0%）、平均 3.308 秒。三轮串行都没有多发摆风角度，全答三轮均保留这个错误。全答英文新题为 19/24（79.2%），中文题为 18/24（75.0%）；规范串行满分仍不能替代尚未测试的扩展题串行表现。

**H2O 在最初三款开源模型中规范基线成绩最高，但完整请求耗时较长。** 规范为 18/20（90.0%），Strands 为 4/20（20.0%），Liquid 为 0/20（0.0%）。H2O 串行整组为 54/60（90.0%）、平均 6.288 秒；全答为 54/60（90.0%）、平均 6.162 秒，同批 KnowLine/Clef 全答分别为 1.007/3.308 秒。H2O 的 60 组可比较任务中，0 组因布局改变了选择。原序英文诊断为 9/10（90.0%），英文新题为 22/24（91.7%），中文题为 23/24（95.8%）。其扩展表达表现与规范成绩、延迟需要分别比较；当前分字段评分配置的耗时不能靠合并成一次 HTTP 请求直接消除。

按本规范验收时，模型既要选对用户要求的动作，也要对其余字段选择 omit。关闭值 0 是实际设置，与保持不变不同；摆风与自清洁等语义相近字段仍按规范标准答案验收。拆分、合并问题会改变上下文、内部调度或数值计算路径，所以必须同时检查原始选择与延迟。

历史[五模型提示词与两阶段对照](AC_CONTROL_COMPARISON.md)、[Liquid 优化](LIQUID_AC_OPTIMIZATION.md)和[H2O 优化](H2O_OFFICIAL_OPTIMIZATION.md)分别保留。本轮统一 baseline，没有对全部九模型重跑历史五种提示词方案。两阶段先判断 apply/omit 再选择 Value，和逐字段直接选 Value/omit 的 30 步串行是不同流程。
