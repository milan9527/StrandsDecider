# 空调控制九模型输入压缩完整实测

## 先看结论

**不建议把这两种压缩写法作为九模型统一的默认输入：多数模型虽然更快，完整任务准确率却明显下降。** 保留完整能力表，并不足以替代清晰的局部任务指令和 omit 条件。

GPT 的三种输入在规范场景的全答和串行测试中均为 100%。紧凑表版本的全答平均输入从 5,223.1 降至 3,217.1 tokens（减少 38.4%），耗时从 2.449 秒变为 2.475 秒。它保住了本批场景的准确率并节省输入 tokens，但本轮没有体现出端到端加速。

这轮实验验证了两种具体的输入压缩写法。能力表、候选和离线判分标准保持完整，**是否适合采用仍须看实际准确率，不能仅凭 tokens 减少判断优化成功。**

## 输入与判分

- baseline：原始完整能力表、字段说明及选项描述。
- compact_catalog：保留原始能力表，集中公共规则，精简字段及选项描述。
- schema_once：完整能力表在 state 中使用列名加数据行的紧凑表示，问题与 compact_catalog 相同。每个内部评分任务都能读取完整映射。
- 全部版本保留 30 项能力和 283 个现有候选（含每字段一个 omit，共 30 个）；数值范围沿用整数候选，范围单位、状态限制与温标伴随规则不变。
- 九模型统一使用字符串选项描述；数值描述为数值 ID，与此前 Clef 专用 None 描述的离线版本不同。
- 按整条命令集合严格判分；多发、漏发、错误值均失败。单字段准确率与完整任务准确率分开。
- 大多数未要求字段应选 omit，因而单字段准确率可能很高；判断是否满足控制需求，应看完整任务准确率。
- 单步：一次请求选择一个字段；30 步串行：对同一个 Query 依次请求全部 30 个字段，合并成一条命令集合，不把上一字段答案传给下一步；一次全答：一次提交全部 30 个字段。三者均保留完整能力集，串行不是连续执行 30 条不同用户指令。
- 每个版本测试 20 个规范场景，每种布局重复三轮；60 次完整任务对应 20 个不同场景。
- 每版本另有 156 次质量请求，含规范、诊断、英文改写和中文对应题，以及两种选项顺序。
- 原始输入也重新实测；不同版本的运行顺序按模型轮换，保留原生缓存与相同预热流程。

## 为什么保留完整能力表，准确率仍会下降

第一种压缩 `compact_catalog` 的 state 与 baseline 完全相同，变化只发生在问题说明和候选描述；第二种压缩才进一步改变能力表的表示。因此，第一种方案出现的退步已经说明：保留信息并不等于保持模型对任务的理解。

以 Power 字段为例，原始问题显式要求从 query 选择请求的值，未请求则选 omit；精简后主要保留名称和功能区分，选择规则集中在公共 state。omit 的描述也从“Do not send t_power: Power is not requested.” 缩为 “No change.”。全局规则仍存在，但局部任务指令的重复和候选措辞对这些模型可能很重要。本轮同时改动了问题指令和选项描述，没有单独隔离其中某一句的因果作用。这两种写法精简得较激进；实验未覆盖“只压缩能力表、保留原始问题和 omit 描述”，因此不能据此认定所有输入压缩都无效。后续应先做小规模单因素对照，通过准确率检查后再做完整耗时测试。

## tokens 减少为什么没有等比例加速

- 九模型的 usage 口径不同，横向比较绝对 tokens 不能直接比较计算量。本报告的压缩比例均在同一模型内计算。
- 每个版本仍有相同的 30 个字段和 283 个候选；前向次数、候选评分、分组选择、CPU/HTTP 开销及固定图长度不会随文本长度同比缩小。
- Perplexity 沿用官方 CUDA graph 的固定长度桶（2,048/4,096/8,192/16,384）。输入缩短未必改变执行所用的桶。
- GPT 仍需输出同样的字段 JSON。其报告的输入量包含缓存读写；减少逻辑输入量不代表每次都减少相同数量的实际预填充计算。
- KnowLine 三个版本的实际 prompt 均已离线重建：每版本核对 1,860 次正式请求，tokens 全部匹配。此次全答均未重复输入，600 种单字段布局均重复输入，没有因压缩跨过 read-twice 阈值；同一布局压缩前后的准确率变化不能归因于这项开关切换。

## 整轮实验为何耗时较长

整轮实验耗时与单次决策延迟分开核算。之前九模型共 18,441 次调用，本轮对照为 55,323 次，另有一次不计入最终成绩的 Jev 早期试跑 2,049 次。每版本的 2,049 次仍由 1,800 次单字段、156 次质量、60 次正式全答和 33 次预热组成。

从首个对照开始到最后一个对照结束，共 **10.89 小时**。其中 27 组脚本运行时间合计 9.37 小时，早期 Jev 试跑 2.25 分钟，调度中断导致额外空等 **72.01 分钟**，其他启动、归档和阶段切换约 17.34 分钟。

调度脚本曾在 SSM 命令提交后过早查询状态，将暂时查不到记录误判为失败。Strands 实际已启动，直到恢复调度才开始推理。修复只涉及基础设施轮询和断点恢复，没有改动冻结推理代码，也没有重试模型请求。故障记录已保留，未算入模型响应时间。

托管 API 与 GPU 也采用全局串行，使总时间累加；独立资源本可并行，同时保持单模型请求串行。本轮保留既定顺序，以便所有数据使用同一协议。此次 EC2 按用户要求保留运行，自动停机已取消。
