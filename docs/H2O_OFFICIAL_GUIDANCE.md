## 1. 双向模式不使用前缀缓存

官方明确写道：

> reads nothing from and writes nothing to the prefix cache (a two-way prefix is not reusable)

并建议单向模式用于：

> when many questions share one long record and every read should use the prefix cache

双向模式需要整段 prompt 一次 prefill，不支持 chunked prefill，既不读也不写前缀缓存。其状态表示受后面的问题和选项影响，不能把同一文本前缀当作可复用的 causal 前缀。

当前空调请求恰好是同一状态对应 30 道题；shim 为每题构造一次推理。不能靠打开一个缓存参数让双向模式共享这段计算。本项目 S03 中双向／causal 的 `processed_input_tokens` 为 40,137 / 6,468，与官方所述缓存行为相符；该字段仍不等于独立测得的缓存命中率或全部耗时分解。

官方默认仍推荐双向模式做决策；causal 是有明确适用条件的另一模式，不保证答案与双向一致。我们测得 causal 5.853→1.692 秒，但诊断题 10/10→8/10，尚不能切换默认。

## 2. 单题与多题，缓存策略不同

`SHIM_CACHE_WRITE` 仅影响单向读取：

| 值 | 含义 | 官方建议 |
|---|---|---|
| `all` | 每题都允许写入前缀缓存，默认 | 多题请求保留此配置 |
| `first` | 多题请求只有第一题写；单题请求不写 | 低负载、每次只有一题时可以测试 |
| `none` | 每题均不写，仍可读取已有缓存 | 文档未推荐为多题默认 |

官方 L40S 实测：单题、800–1,200 token，`first` 将耗时 65.1→51.1 ms；但三题请求在所有已测负载下吞吐都降低。因此“外部请求串行”不足以说明该选 `first`：本项目一次请求有 30 题，应以 `all` 为对照。若另测单 Key 串行，才单独评估 `first`，不能混合计时口径。

## 3. 官方量化与硬件口径不同于当前部署

官方参考与校准基于 BF16；FP8 是可选的吞吐优化，并明确会改变部分选择。官方某个 H100、较早权重的实验中，687 题有 21 个答案改变，不能把这一比例直接套用到我们的空调测试。

当前为 L4 24GB、三模型常驻，H2O 使用 FP8、`GPU_UTIL=0.34`、`seq=1`、eager。官方速度表来自 H100 80GB／L40S 48GB，且分别标明单题／三题、输入长度、并发、权重版本；不对应我们完整 30 题的约 6 秒。

例如官方 L40S 在 800–1,200 token、单题、一次一个请求时，双向 P50 为 59.7 ms，单向为 69.3 ms。这也说明 causal 并非每种输入都天然更快；共享状态、执行配置和缓存条件必须一起看。

BF16 对照有助于区分模式变化与量化影响，但不能仅凭官方提示把本次重启差异归因于 FP8，也不能保证 BF16 更快。当前三模型共享显存下不能直接照搬官方部署，需要单独的资源评估和质量对照。

## 4. 图、批次预算和补丁都有适用边界

| 项目 | 官方说明 | 本项目含义 |
|---|---|---|
| GDN prefill 图 | 默认覆盖至 2048 token，额外约 1.1GB；24GB GPU 建议 `VLLM_GDN_PREFILL_GRAPH_MAX_TOKENS=1024`，约 0.5GB，或降低 GPU_UTIL；0 为关闭 | 当前关闭；此前试的是4096，不是官方给24GB卡的1024档。1024档尚未测，也未必覆盖本批每题的实际长度 |
| 整步 CUDA graph | 双向默认512；L40S把512增到2048没有可测延迟收益，启动更慢 | 不应继续假定图越大越快；当前eager不能只看图上限值判断已经启用 |
| 批次 token 预算 | 双向需整段处理，`serve.sh` 最后强制传入 `--max-num-batched-tokens MAX_LEN` | 当前实际4096；只在 `VLLM_ARGS` 写8192会被覆盖。官方8192建议主要针对单向并发吞吐 |
| 两个调度／GDN补丁 | 官方 per-request-attention 构建已包含 | 我们已使用对应构建；不用重复打补丁。`VLLM_PATCHES=1` 用于stock vLLM，官方构建会拒绝该设置 |
| CPU | 官方短输入 profiling 显示CPU可成为瓶颈，建议避免其他CPU重任务占用引擎物理核心 | CPU亲和性／占用值得测；尚不能据此认定我们的约6秒由CPU争用造成 |

官方给出的吞吐提升与多请求在途参数，不等于单个空调任务的延迟改善。后续测试仍应保持外部任务串行，记录同一任务内部的实际批处理。

## 5. 编译缓存须按配置隔离

官方指出 vLLM 0.30 的编译缓存键没有包含全部影响执行的配置，跨配置复用图曾导致失败或读取结果改变。`serve.sh` 在未显式指定 `VLLM_CACHE_ROOT` 时，按构建、模式、长度、图、图像设置和额外引擎参数生成独立目录。

本项目常驻配置显式固定 `/bench/h2o-cache`，覆盖了自动命名；后续若换配置，应使用不同目录。此前正式优化实验已经为不同方案设置独立缓存目录，标准编译使用新目录。因此该官方说明是一项后续核验要求，**不能把此前 N09 跨重启变化直接判定为旧编译缓存污染**。前缀缓存、GDN prefill 图与磁盘编译缓存是不同机制。

## 调整后的实验建议

先固定当前权重、官方补丁和输入，建立重启后可复现的对照；在资源允许的独立环境比较 BF16／FP8，避免把当前FP8成绩当作官方BF16参考。

延迟方向优先验证 **causal＋默认 `SHIM_CACHE_WRITE=all`**，并与双向逐题比较完整指令。causal 是官方针对共享长状态多题的明确建议；是否能通过通用规则澄清改善已知回退，仍需冻结新问题后实测。

另测符合24GB卡限制的 GDN 图档位、独立配置缓存和CPU条件。保留30项能力与全部合法候选，不以减少测试能力或提高外部并发来制造加速结果。文档给出的设置不是本项目已经验证通过的配置。

本项目历史实测与当前限制见 [H2O_OPTIMIZATION.md](H2O_OPTIMIZATION.md)。本文为文档核对；随后执行的[官方建议优化实测](H2O_OFFICIAL_OPTIMIZATION.md)已完成，因果与 GDN 1024 均未通过采用门槛，原服务已恢复。
