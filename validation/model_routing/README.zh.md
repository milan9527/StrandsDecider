# 类 OpenRouter 模型选择：Jev / Decider 实测

2026-10-13，完成 **224 次真实决策调用**。实际模型为 `jev-1.13.0` 和 `strands-decider-2B-hobson-v19`。没有调用被选中的下游模型，没有调用 `openrouter/auto`；本报告测量的是**按给定任务与政策选路由的能力**，不是 OpenRouter 本身的效果，也不是下游回答质量。

**结论：两个模型都适合进一步试点“用户任务 → 路由类别”。Jev 在复合路由政策上优于当前 Decider，但两者都不适合独立承担能力过滤、预算计算、可用性检查和最终模型选择的全部职责。只把 JSON 改写成自然语言没有解决问题。**

## 与 OpenRouter 哪一部分相似

本次读取并保存了 OpenRouter 当日公开文档与模型目录：

- [Auto Router](https://openrouter.ai/docs/guides/routing/routers/auto-router)：当前文档描述先分类任务，再按对应任务近七天的市场支出份额排序，应用成本档位、限制条件与回退。不能把它概括为仅向一个模型问“选哪个最强”。
- [Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection)：提供模型供应商层面的价格/延迟排序、参数要求、数据策略和回退设置。模型选择与同模型的供应商选择是不同层次。
- [Models API](https://openrouter.ai/api/v1/models)：作为能力与标价的冻结来源。

本实验模拟应用的两层路由：第一层识别任务类别，第二层按明确政策选择实际模型 ID。价格、能力和上下文来自目录；请求、端点健康、限流、延迟与零保留标记由测试构造，**不代表真实供应商当时的状态或隐私承诺**。

本测试的“最便宜”“首个合格模型”和预算公式是明确规定的应用政策，不能等同 OpenRouter 默认负载均衡或市场排序。软延迟偏好保留“没有达标候选时仍可使用其他候选”的含义。

## 测试设计

32 道题，四类各 8 道：

| 类型 | 实际问题 |
|---|---|
| 任务语义分流 | 普通改写、简单标签、并发代码分析、死锁诊断、数学证明、发票图片、长合同、附件缺失 |
| 能力约束 | 图片/音频/视频输入、30 万 token 上下文、7 万 token 输出、图片＋logprobs、工具＋结构化输出、图片生成无候选 |
| 成本与预算 | 最低成本、输入密集、输出密集、预算不足、刚好等于预算、仅一项可负担、长上下文阶梯价、推理参数＋长输出 |
| 可用性、回退与偏好 | 主模型故障、429、禁止回退、全部故障、账号排除、零数据保留要求、软延迟无人达标、达标池内选最便宜 |

首轮每题测试原始和反转候选顺序，两模型各 64 次，共 128 次。收到首轮结果后，另固定一份对照计划，只将后 24 题的候选 JSON 属性改写为自然语言；状态、政策、字段事实、参考答案、候选 ID 和候选数量保持不变。对照为每模型 48 次，共 96 次。语义分流本来就是自然语言，不在第二批重复。

每个“题目＋顺序＋表达”配对给两个模型的输入完全相同，输入 SHA-256 已核对。无自动重试、候选预筛选、规则代选或模型回退；标准答案只用于评分。第二批是首轮之后的诊断，不是独立测试集，也没有挑成功案例替换首轮结果。

## 结果：不能把任务分类成绩当成完整路由成绩

每格为符合参考数 / 回答数。**每类只有 8 道独立题，两种候选顺序产生 16 次回答。**

| 场景 | Jev：JSON 候选 | Decider：JSON 候选 | Jev：自然语言候选 | Decider：自然语言候选 |
|---|---:|---:|---:|---:|
| 任务语义分流（本身已是自然语言） | 15/16 | 16/16 | 未重复 | 未重复 |
| 能力约束 | 7/16 | 3/16 | 7/16 | 2/16 |
| 成本与预算 | 9/16 | 2/16 | 9/16 | 2/16 |
| 可用性、回退、延迟偏好 | 15/16 | 4/16 | 15/16 | 4/16 |
| 后三类合计：24 道题 | **31/48（64.6%）** | **9/48（18.8%）** | **31/48（64.6%）** | **8/48（16.7%）** |
| 首轮全部四类：32 道题 | **46/64（71.9%）** | **25/64（39.1%）** | — | — |

只看原始候选顺序：

| 场景 | Jev | Decider |
|---|---:|---:|
| 任务语义分流 | 7/8 | 8/8 |
| 能力约束 | 5/8 | 2/8 |
| 成本与预算 | 6/8 | 1/8 |
| 可用性、回退、延迟偏好 | 8/8 | 2/8 |
| 合计 | 26/32 | 13/32 |

语义分流仅差一次回答，不能据此判断 Decider 普遍强于 Jev。Jev 将“改写已提供的通知文本”选为补充材料，反转顺序后选对；该题用任务描述声明文本已提供，没有附上全文，可能增加歧义。本报告按原定参考保留分数，并注明这一局限。

## 错误是什么，会怎样影响路由系统

### 有候选却拒绝，是本批 Decider 的主要问题

后 24 题中，20 题应选具体模型、4 题应拒绝路由。两种顺序共有 40 次应正常路由的机会。

| 行为 | Jev：JSON | Decider：JSON | Jev：自然语言 | Decider：自然语言 |
|---|---:|---:|---:|---:|
| 有合格候选却选择 `no_route` | 9/40 | 37/40 | 9/40 | 40/40 |
| 选了违反硬约束的模型 | 5/48 | 2/48 | 5/48 | 0/48 |
| 模型合格，但未按成本/偏好排序 | 3/48 | 0/48 | 3/48 | 0/48 |

自然语言批次中，Decider 的全部 48 次回答都是 `no_route`，只有 8 次碰巧符合确实无候选的题目。它的硬约束违规数为零，不能解读成可靠：同时拒绝了全部 40 次可处理请求。

具体例子：Flash 测试端点故障，但 Pro 在允许列表内且健康，Jev 选择 Pro；Decider 仍选择无路由。正常的小型文本请求，目录里有健康、低价且容量足够的模型，Decider 也多次拒绝。

### Jev 也会漏掉能力和预算约束

图片输入题中，Jev 在原顺序下选择仅支持文本输入的 Llama 候选；反转顺序后又误选无路由。30 万 token 输入题的 JSON 原顺序中，两者都选择容量为 131,072 的 Llama，超出本题应用规定的上下文上限。

输出密集的价格题中，允许的两模型为：

| 候选 | 输入 USD/百万 token | 输出 USD/百万 token | 1,000 输入＋10,000 输出的题目估算 |
|---|---:|---:|---:|
| Qwen3 Coder 30B A3B | 0.07 | 0.28 | 0.00287000 USD |
| Mistral Small 3.2 24B | 0.09375 | 0.25 | **0.00259375 USD** |

Jev 两种表达、两种顺序均选择 Qwen；它输入单价较低，但本题总成本较高。预算恰为 0.00259375 USD 的题目中，选择 Qwen 还违反预算。Decider 则选择无路由，虽然 Mistral 正好满足包容等号的预算约束。

这些是按固定公式比较给定数字的错误，没有测量真实账单。题目成本不含缓存、媒体、工具、隐藏推理用量等费用；目录模型级价格也不保证每个具体供应商端点都以相同条件可用。

### 顺序稳定不等于判断正确

首轮 32 题中，Jev 有 10 题在反转候选后改变回答，Decider 有 3 题。自然语言的 24 题中为 9 题和 0 题；Decider 的“0”来自两种顺序都拒绝全部请求，不能作为优势。

仅改变表达后，Jev 在后三类的合计仍为 31/48，但具体错题有变化；Decider 从 9/48 变为 8/48。这里没有证据支持“改成自然语言就能解决完整模型路由”。

## 速度、调用有效性和诊断边界

| 指标 | Jev | Decider |
|---|---:|---:|
| 首轮语义分流请求中位 RTT | 134.4 ms | 101.4 ms |
| 首轮全部请求中位 RTT | 137.4 ms | 211.4 ms |
| 首轮全部请求 P95 RTT | 173.1 ms | 219.2 ms |
| 自然语言政策批次中位 RTT | 132.7 ms | 219.2 ms |
| 两批成功调用 | 112/112 | 112/112 |

Jev 直连现有 API，Decider 走现有服务网关；这些是部署路径下的往返耗时，不是纯推理时间。没有下游模型回答耗时、质量或费用，不计算“端到端节约了多少钱”。

首轮 Decider 报告的输入最多 1,422 tokens，自然语言批次最多 1,485，低于服务公布的 4,096 上限；没有 API 失败。现有记录不支持把表现归因于超出该上下文上限，但仍不能确定模型训练、输入结构、拒绝选项措辞等因素各自贡献多少。

## 对 OpenRouter 式产品的具体建议

**把任务理解交给决策模型，把明确约束交给代码。**

```mermaid
flowchart LR
    A[用户请求与附件] --> B[Jev 或 Decider：识别任务类型]
    B --> C[按业务评测选择合适模型池]
    C --> D[代码检查能力、上下文、预算、可用性]
    D --> E[按明确策略排序与回退]
    E --> F[调用下游模型并记录质量、成本、时延]
```

| 职责 | 本轮支持的用法 |
|---|---|
| 判断是普通改写、代码诊断、数学证明、图片读取 | 两者都可试点；Decider 在本组表现很好，需更大真实请求集 |
| 在已合格的少量模型间按业务语义选档位 | 值得单独验证；本轮没有测试这种前置过滤后的组合系统 |
| 校验图片、工具参数、上下文、输出上限 | 使用模型目录与端点能力的确定性检查 |
| 比较输入＋输出总价、执行预算上限 | 使用代码；本轮两模型均有错误 |
| 处理供应商宕机、限流、禁止回退、数据策略 | 用服务运行状态和明确回退逻辑；Jev 可辅助，但不能替代硬条件 |
| 判断“哪一个模型实际答得最好” | 需要下游回答与业务质量评测；本轮没有证明 |

因此，如果需求是“给请求打任务标签，再交给网关选模型”，两个决策模型都值得继续评估；如果需求是“把完整模型目录、预算和故障状态交给模型，让它一步做完”，**当前实验中 Jev 较好，但两者都未达到可独立采用的水平**。

这份分层架构是基于失败模式提出的设计建议，不是已经跑出新成功率的系统。程序约束如果参与未来实验，应分别报告模型原始选择、程序调整次数与最终任务结果，不能把代码修正后的成功都计到模型头上。
